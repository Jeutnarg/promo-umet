	FIRST PROMPT
		DIRECTION
		You are an architect working with a senior engineer. You may challenge design decisions but not the domain or goals. Everything must work locally but also be easily transitioned to cloud hosting. If feasible, include infrastructure as code for the full system, assuming AWS where an assumption must be made.
		
		GUIDING PRINCIPLES
			We care about stable and scalable architecture and maintainability above all. Code must be well-structured, with repetitive code in both tests and main extracted. Comments should be terse and not normally present within a method.
	
		OVERVIEW
		We are creating a four-part system. The first part is a simple database (probably NoSQL) resource which acts as the source of truth. The second is a web service which holds core logic, acts as a judge of correctness, and supports the frontends. The third is a thin frontend which serves users. The fourth is a thin frontend which serves administrators. There is a fifth, implicit service for authorization/authentication. This overall system could be prepared for deployment soon, and so security must be incorporated from initiation.
		
		For now, let us assume...
			That our final product uses a cloud-based NoSQL service such as Redis or DynamoDB for the resource component. The final product will use an Amazon-hosted Java SpringBoot service as the backend component. The final product will use a Typescript framework for both frontends. The final product will use OAuth for authorization/authentication, but this assumption is weak.
		
		
		THE DOMAIN
		We are creating a system to allow users to load a cart with items of particular quantity and price as well as apply promotions in a variety of types. Promotions are applied to the cart as selected. A final price is calculated and displayed to the user as they move through the process. The user has the cart/order page, the confirmation page, and the order complete page, which has an option to navigate to a fresh cart page or a cloned cart page to repeat an order. An admin has the promotions control page and the promotion test page. The promotion test page allows for the construction of test sets based on files or copy-pasted in as well as manual entry (which can then be saved to a file and incorporated into a new or existing test set.) At any phase in either testing by admin or usage by user, the promotion logic must be transparent; the users must know which promotions applied and how much money they saved. There should be a "Suggest" function which calculates the optimal promotion application strategy and a "Swindle" option which displays the least-optimal promotion application strategy which still applies at least one to every item if possible. Promotions have expirations, and an expired promotion should be removed with a small banner notification. When displaying multiple promotions on a single item, order by largest savings descending.
		
		POTENTIAL CONFLICTS
			The suggested rules library may not have the flexibility to do what we need. Feel free to pivot from that.
		
		TESTING PRINCIPLES
			UNIT TESTS
				Unit tests for a method use parameterized inputs to test edge cases and several interior cases.
				Unit tests for a method which calls another method test that the method is called when the condition for calling it is true (may be implicitly true always if not conditional).
				Unit tests for a method which calls another method test that the method is called with the correct parameters.
				Unit tests for a method which calls another method test that the method's response is correctly passed to the next stage.
				Unit tests for a method which calls another method do not test internal behavior.
				Unit tests use terse comments to describe their purpose.
			COMPONENT TESTS
				Tests validate every exposed endpoint's full set of flows. A flow is defined as a unique ordering of downstream resource accesses, meaning that a GET call which can either call the database once or twice has four flows. Flow 1 - FAILURE. Flow 2 - SUCCESS. Flow 3 - SUCCESS FAILURE. Flow 4 - SUCCESS SUCCESS. The tests should use the @SpringBootTest approach, use Java code to generate mock files in a fluent format, have Gherkin comments, and set unique data for every endpoint in order to prove that each endpoint was reached as expected.
		
		MODELS
			Item - name, quantity, price, category
			Carts - user, list of items
			User - name, login details, list of carts, isAdmin
			Promotion - name, scope, exclusivity, strategy, strategy details (key-value), expiration
			
		PROMOTION STRATEGY EXAMPLES
			bogo - buy one get one of equal or lesser value free
			flat - reduces price by constant
			flatgoal - reduces price by constant if total after promotions (not including itself) exceeds constant.
			shippinggoal - reduces price by cost of shipping if total after promotions (not including itself) exceeds constant
			rainbowpercent - reduces price by percentage if number of categories equals or exceeds constant
		
		PROMOTION SCOPE EXAMPLES
			oneitem - only applies to one item
			item - applies to all of one item
			items - applies to entire order except shipping
			order - applies to entire order
